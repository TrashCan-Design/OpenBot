1. EXECUTIVE SUMMARY & PROBLEM OVERVIEW
--------------------------------------------------------------------------------
Executing a simple user prompt such as "Can you open Firefox and Wikipedia and in
it search for World War I" currently takes ~8 minutes (480 seconds) in OpenBot.

A static and architectural latency audit reveals that this latency is not caused
by model inference speed alone, but by a combination of five compounding architectural
bottlenecks:
1. Surface Routing Failure: Tasks with web intent are routed away from the built-in
   fast CDP/DOM browser engine to OS desktop mouse/keyboard emulation because
   server/surface.ts disables the browser unless botOpened is true.
2. Banned Batch Actions: server/computer-tool-list.ts explicitly drops run_steps
   and run_script, forcing every individual mouse move, click, keystroke, and
   screenshot into a separate LLM turn (18 to 22 turns for a simple task).
3. Massive Payload Bloat: server/container-computer.ts captures unscaled,
   uncompressed 1080p PNG screenshots (2MB–5.5MB base64 each) and appends them
   into conversation history up to 32MB without downscaling or lossy compression,
   causing HTTP upload stalls and multiplying vision Time-To-First-Token (TTFT) by 10x.
4. Silent Image Discard on Custom ACP: server/drivers/acp/custom.ts omits
   "images: true", causing ACP block parsing in server/drivers/acp/core.ts to strip
   all screenshots (images=0), leaving Mistral and custom ACP agents blind and
   trapped in 3–5 minute hallucinated retry loops.
5. System Prompt Coordinate Hunting Bias: Prompts in server/system-prompt.ts and
   server/surface.ts instruct models to perform pixel coordinate searches and forbid
   direct CLI or shortcut URL launches (e.g. firefox <url> or Ctrl+L).


2. TIME BREAKDOWN ESTIMATE (WHY ~480 SECONDS HAPPENS)
--------------------------------------------------------------------------------
When executing via OS desktop emulation without batching or CDP tools, the task
requires 18 to 22 sequential turns:
- Turn 1-2   : Inspect desktop state, locate Firefox icon.
- Turn 3-4   : Move cursor to Firefox icon, double click.
- Turn 5-6   : Settle delay, capture desktop state to verify Firefox window opened.
- Turn 7-8   : Inspect window state, locate address bar coordinates.
- Turn 9-10  : Click address bar, wait for cursor focus.
- Turn 11-12 : Type "https://en.wikipedia.org", press Return.
- Turn 13-14 : Settle delay, capture screenshot to check if Wikipedia loaded.
- Turn 15-16 : Inspect DOM/vision state for search box coordinates, click search box.
- Turn 17-18 : Type "World War I", press Return.
- Turn 19-20 : Settle delay, capture screenshot, read article headline, formulate answer.

LATENCY PER TURN BREAKDOWN (AVERAGE):
--------------------------------------------------------------------------------
1. Container Screenshot & Base64 Pipe: ~2.2s
   - Execution of cua call get_desktop_state inside container: ~1.2s
   - Execution of base64 -w0 /tmp/openmausbot-preview.png: ~1.0s
2. Payload Serialization & Network Upload: ~4.5s
   - Cumulative conversation history containing 5MB-25MB of base64 PNG data.
   - Uploading 10MB-25MB over standard HTTPS connections takes 3.0s - 6.0s.
3. LLM Vision TTFT (Gemini 3.8 Flash High / Mistral): ~9.5s
   - Vision encoder tiles high-resolution 1080p images into dozens of sub-patches.
   - Thinking level "High" reasons across multiple visual artifacts: ~7.0s - 12.0s.
4. Tool Execution & MCP Stdio Proxy: ~1.5s
   - Node proxy dispatch, JSON-RPC framing, xdotool / input delivery: ~1.0s - 2.0s.
5. Settle Delay & Screen Poller Sync: ~2.0s
   - Hardcoded post-action delays, pokeScreenPoller, finalScreenFrame checks.
Average Latency per Turn: ~19.7 seconds.

TOTAL ACCUMULATED TIME ACROSS 20 TURNS:
--------------------------------------------------------------------------------
- 20 turns x 19.7s/turn                                 = ~394s
- Coordinate misses / re-read retries (2 occurrences)   =  ~50s
- Driver cold start / OAuth & contractKey verification =  ~16s
- agent-browser / CDP laneWaitMs queue hang             =  ~20s
--------------------------------------------------------------------------------
TOTAL TASK EXECUTION TIME:                                = ~480s (~8 minutes)


3. ROOT-CAUSE FINDINGS BY SUBSYSTEM (WITH EXACT FILE PATHS & LINE NUMBERS)
--------------------------------------------------------------------------------

3.1 Subsystem 1: Execution Surface Routing & Banned Batching
------------------------------------------------------------
- File: server/surface.ts (Lines 61-84, function placeOf)
  * Mechanism:
    When a bot destination is set to "local" or "vm", line 66 computes:
    `const beside = input.botOpened === true && browserOn;`
    For normal user chats, input.botOpened is undefined / false.
    Consequently, line 81 returns:
    `{ computer: destination, browser: false, pinned: null, note: "" }`
  * Impact:
    In server/index.ts (lines 8414-8424), integrations.browser is completely omitted
    because plan.browser is false. Web tasks are therefore prevented from accessing
    the built-in Chromium CDP engine (browser_navigate, browser_snapshot, browser_click)
    and are forced into full OS desktop vision/mouse emulation.
- File: server/computer-tool-list.ts (Lines 15-27)
  * Mechanism:
    Line 17 defines:
    `const BATCH_RUNNERS: ReadonlySet<string> = new Set(["run_steps", "run_script"]);`
    Line 26 filters them out:
    `return !DRIVER_UPKEEP.has(name) && !BATCH_RUNNERS.has(name) ...`
  * Impact:
    The model cannot batch actions (e.g. click + type + press Enter). Every atomic
    action requires an independent LLM turn, expanding a 2-turn task into 20 turns.

3.2 Subsystem 2: ACP & Custom CLI Driver Overhead
-------------------------------------------------
- File: server/drivers/acp/custom.ts (Lines 14-30, AcpSupport definition)
  * Mechanism:
    `images: true` is missing from the AcpSupport object.
  * Impact:
    In server/drivers/acp/core.ts (lines 1449-1451):
    `const imageBlocks = support.images === true && runtimeAcceptsImages ? await readAcpImageBlocks(turn.images ?? []) : [];`
    Because support.images is undefined, imageBlocks is always empty ([]).
    When running Mistral (vibe-acp) or custom ACP engines, the model receives zero
    visual feedback (images=0), leading to blind clicking, target misses, and 5-minute
    hallucination loops.
- File: server/drivers/antigravity-acp.ts (Lines 227-250) & server/drivers/acp/core.ts (Lines 1120-1137)
  * Mechanism:
    contractKey mismatches (due to tool scoping or cwd variations) cause
    closeSession(threadId, "contract") to terminate the session, triggering a full CLI
    cold start. Cold-starting Google's packaged Antigravity server (Python/V8 unpack,
    OAuth tokens) adds 5–15 seconds per session reload.

3.3 Subsystem 3: Screenshot & Vision Pipeline Bottlenecks
---------------------------------------------------------
- File: server/container-computer.ts (Lines 1034-1058, containerComputerFrame)
  * Mechanism:
    Captures a full 1080p/Retina screenshot via cua call get_desktop_state and reads
    it using `base64 -w0 /tmp/openmausbot-preview.png`.
    Unlike server/vps-computer.ts (lines 56-62, which uses Pillow to downscale to 1280x1280
    JPEG quality 70), container-computer.ts transmits unscaled, uncompressed raw PNGs.
  * Impact:
    Produces 1.5MB–4MB raw binary PNG files (2MB–5.5MB base64).
- File: server/drivers/chat-images.ts (Lines 7-20 & 30-44)
  * Mechanism:
    Allows up to 20MB per image and a 32MB budget (CHAT_IMAGE_BUDGET = 32 * 1024 * 1024)
    without downscaling or lossy compression before JSON serialization.
  * Impact:
    Over 10-15 turns, message history exceeds 25MB. Uploading this payload adds 3–6s
    per turn, while LLM vision tile processing inflates TTFT to 8–15s per turn.
- File: server/index.ts (Lines 6498-6503, 6910-6922, and Line 7521)
  * Mechanism:
    `SCREEN_SETTLE_TIMEOUT_MS = 10_000`. Every desktop action triggers screen poller
    sync and settle timers, adding 1,000ms–2,500ms of dead wait time per tool call.

3.4 Subsystem 4: Browser Engine & Daemon Timeouts
-------------------------------------------------
- File: server/browser-runtime.ts (Lines 55-65 & 437-479)
  * Mechanism:
    `laneWaitMs` is hardcoded to 30,000ms (30 seconds). agent-browser serializes commands.
    If an action or CDP connection stalls, subsequent operations block for 30s.
- File: server/browser-engine.ts (Lines 83-108, runBrowserCommand)
  * Mechanism:
    Enforces a 5,000ms SIGTERM-to-SIGKILL grace period on process termination. Zombie
    Chrome processes holding profile locks cause commands to hang for 15s–35s.

3.5 Subsystem 5: System Prompt & Tool Selection Bias
----------------------------------------------------
- File: server/system-prompt.ts (Lines 110-112, SANDBOX_DESKTOP_INPUT)
  * Mechanism:
    Explicitly instructs:
    "On this desktop, read a window with get_window_state before acting on it and take
    x,y from that window's own screenshot... If an accessibility type or click changed
    nothing, read that window again and type in the foreground..."
  * Impact:
    Biases models toward slow human-like pixel hunting rather than fast keyboard
    shortcuts or direct programmatic navigation.
- File: server/surface.ts (Line 156, SURFACE_AUTHORITY)
  * Mechanism:
    "Do not substitute the provider's own desktop, a shell-launched browser, or another
    automation path for the selected OpenBot surface."
  * Impact:
    Forbids models from using single-step commands (e.g. firefox "https://en.wikipedia.org" &),
    forcing tedious step-by-step GUI clicks.
